Why it repeats

A straight line, or a loop.

A session holds no state. Nothing survives it — so on the left, the answer is the end of the picture. On the right, the same session reads what earlier ones left behind, and leaves something itself.

Same model, same session length. The loop is the only difference.

Working with Databricks

Five ways to run something.

Claude Code sits on the laptop and never runs inside Databricks. Every one of these is an API call going out. What changes is which steps happen on which side.

runs on the laptop runs in Databricks you, in the browser spends money — needs you to say go
1
SQL over the API
writes SQL→warehouse runs it→rows come back
Checking a column, a count, whether a join duplicated anything. Nothing starts and nothing costs.
2
Hybridmost of the work
writes SQL→warehouse runs it→rows come back→Python finishes it here
Way 1, plus the part after: the joins, the percentages, the spreadsheet. No cluster, because the result already fits.
3
A notebook you runhow most work ends
pushes it up→sits in the workspace→you press run→reads the output
Once the investigation is done and the code is worth keeping. You see it before it runs, and you own the run.
4
Serverless job
submits it→runs, no machine to choose→reads the result
When the work has to happen over there and starts in seconds. Costs money, so it waits for your go.
5
Cluster job
submits a spec→machine built→runs→thrown away→reads the result
Only when it needs a particular machine. Costs more and spends the first minutes booting.

The setup itself

Where all of it actually lives.

Two folders on the laptop and one in Databricks. Everything on this page is a file in here — nothing is configured in a settings screen, and nothing is hidden.

On the laptopRules, memory and skills that apply everywhere — plus the work itself.
# applies to every project ~/.claude/ ├── CLAUDE.md rules for every project ├── rules-manual.md how to reason, not what to know ├── settings.json which scripts run when ├── skills/ step-by-step procedures └── projects/<name>/ └── memory/ an index, plus one file per fact # the project you are working in <project>/ ├── CLAUDE.md rules for this project only — wins where they disagree ├── SESSION_LOG.md one line per finding, oldest at the top ├── .claude/ │ └── settings.json the scripts only this project runs ├── scripts/ │ ├── *.py the scripts named in settings.json │ ├── projects/ ongoing work │ │ └── <name>/ │ │ └── STATE.md where this one stands, and what is next │ ├── validation/ checks worth re-running │ ├── adhoc/ one-off work, dated │ └── cache/ copies pulled down to read └── archive/ finished work, moved not deleted
In DatabricksOnly the finished notebook, and what it writes when it runs.
/Workspace/Users/<you>/ │ ├── backups/ │ └── <name>_<date> taken before anything is overwritten │ └── <folder per piece of work>/ ├── the notebook notebooks at this level, nothing else ├── counts/ a subfolder named for what it holds └── outputs/ what the notebook writes # the same name on both sides: # laptop = everything written along the way # here = only the finished thing and its output
the whole idea, in one line

None of this is clever. It is a handful of plain text files in known places, and a few small scripts that read them at the right moment. You can open every one of them, and delete any of them.

Set it up yourself

You do not have to build any of it.

The file below is written for Claude, not for you. Drop it in and it reads your machine, asks what you work on, and builds the whole thing while you watch.

  1. Download the file.
  2. Put it in the folder you work in — the same one you open Claude Code from.
  3. Start Claude Code there and say read README.md and set me up
  4. Answer its questions. It checks your machine first and tells you what it can and cannot do before it changes anything.
README.md22 KB · plain text

Works on macOS and Windows — it has separate instructions for each and will tell you which one it is following. Nothing runs without your say-so.
